Three claims, and the evidence for each

every number below was produced by running the code

The ledger physically refuses to be edited

Balances are never stored — they are summed from append-only entries. Postgres triggers reject UPDATE and DELETE on the ledger tables. Corrections require a mirrored reversal that points back at the original.

Verified from a superuser psql session:
inflate → refused · delete → refused · rewrite narration → refused

Retry timing is solved, not guessed

A dynamic program over the issuer hazard curve, reduced to a suffix maximum so it runs in O(attempts × horizon). No model is involved and there is no escalation path to one — asking an LLM "when should I retry?" is the mistake this track penalises.

From one mid-cycle failure:
insufficient funds → waits 11d 23h to payday
technical decline → retries in 6h

It keeps working when the model fails

With the model entirely unavailable the case still classifies, plans, and recovers in full — on a deterministic fallback that never offers a concession, because pricing a concession was exactly the judgement the model was there for.

39 graph tests over stubbed ports:
model down → recovered · out-of-bounds proposal → refused & counted

What I would do with the three days

ordered by what changes a judge's score
01

README and architecture diagrams

A required artifact and the highest-leverage hour in the whole project. Problem statement, the Mermaid graph diagram, reproducible setup, and an honest limitations section — this track explicitly rewards documented gaps over hidden ones.

required
02

The batch experiment

The track's stated bar is measured money recovered across batches. That needs the simulator's issuer model, the lift statistics, and a make batch that prints a report with confidence intervals — including saying plainly when a result is not significant. Without this the submission misses its own track's headline requirement.

high value

The approval inbox is the only console screen that proves something no test can — that a human really is in the loop. Cut the cockpit, policy studio and replay viewer to static screenshots in the README if time is short.

high value

The pitch video

Five minutes, and the back half should be failure: the model going down mid-demo and recovery continuing, an out-of-bounds proposal being refused, a gateway timeout parking a case instead of guessing. That is the part most submissions skip and the part this rubric names.

required
06

Make Docker actually work

Local development moved to a native Postgres after Docker wedged. The compose file is written but untested, and judges will run it. Verifying it is a small job that removes a large risk.

risk

Two things worth being careful about

UAP has not launched. NPCI's Unified Agent Protocol is expected to be unveiled at Global Fintech Fest 2026 and still needs RBI approval. Anvil models delegated agent authority and Reserve Pay blocks as first-class authorisation objects, which is a genuine strength — but the documentation must say proposed. Claiming to integrate with something that does not yet exist is the kind of error a Razorpay panel will catch instantly.

Depth is bought with breadth. Seven modules are genuinely finished to a standard that would survive code review at a payments company. Four have not been started. The honest framing for the pitch is that this is a deep vertical slice with a documented edge, not a complete platform — and the rubric prefers exactly that, provided the gaps are named rather than hidden.
